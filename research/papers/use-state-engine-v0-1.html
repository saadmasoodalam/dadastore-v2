Universal State Engine

Evidence-Derived State, Guarded Action, and Auditable Mutation

The Universal State Engine (USE) is an experimental state-analysis runtime that derives a layered system state from persisted evidence and produces guarded action recommendations. The current stable prototype is designed around a simple rule: observation and recommendation may be automated, but mutation of live state must remain explicit and auditable.

Scope clarification: This paper describes the currently implemented stable prototype. It does not claim that the engine has universal predictive authority, nor that a recommendation is equivalent to a verified outcome. The runtime operates on persisted evidence, explicit model contracts, validation rules, and recorded feedback.

1. Layered State Derivation

The current implementation evaluates an S1–S8 execution path:

S1 Architecture
→ S2 Signal
→ S3 Structural Validation
→ S4 Reality
→ S5 Feedback
→ S6 Emergence
→ S7 Compression
→ Convergence
→ S8 Action

Layer values use a three-state representation rather than forcing every observation into a binary answer:

1     Active
0     Inactive
NULL  Insufficient validated evidence

The explicit NULL state is important because absence of validated evidence is not treated as equivalent to an inactive condition.

2. The Living State Model

The primary runtime object is the Living State Model. Initialization creates the first version of the model; projection expands it; validation adjusts support and confidence; convergence identifies dominant patterns; action emerges from the resulting state; and feedback updates the model over time.

The architecture treats models as runtime contracts. Engines consume models and produce models; business logic belongs in engines, while data belongs in models. This keeps the state representation explicit and testable rather than allowing unstructured dictionaries or hidden side effects to become the de facto runtime API.

3. Runtime Flow

↓
Identity Engine
↓

↓
Validation Engine
↓

↓

The Identity Engine creates initialization context. Projection produces candidate, emerging, and suppressed states. Validation classifies candidate states as supported, unsupported, or unresolved. Convergence derives confidence and dominant direction. The Action Engine produces guarded recommendations from a bounded action vocabulary, while the Feedback Engine recalibrates confidence and updates state from new observations.

4. Guarded Action Instead of Silent Mutation

The current Action Engine can produce recommendations including OBSERVE, WAIT, BUILD, MOVE, CONNECT, EXPAND, RESET, and EXIT.

However, the architecture deliberately separates:

observation
→ recommendation
→ explicit activation
→ auditable mutation

Read-only analysis must not silently mutate live state. The prototype includes explicit action activation, reality override, structural action blocking, derived-action activation history, and state-transition recommendation history so that the path from evidence to action can be inspected after the fact.

5. Feedback and Confidence Recalibration

Feedback is treated as state evidence rather than an opaque override. The current roadmap evolves feedback from confidence-only updates toward broader changes in action and classification, but the stable prototype already records historical reliability and uses feedback to recalibrate confidence.

This design makes historical performance part of the state process without allowing a single new observation to rewrite prior evidence invisibly.

6. Persistence and API Boundary

The prototype persists its state model in JSON-backed storage and exposes a FastAPI interface. Read-only analysis endpoints are kept distinct from explicit mutation endpoints. Domain-state storage and retrieval allow the runtime to maintain separate evidence contexts while preserving the same execution discipline.

7. Validation Status

The current stable-prototype checkpoint reports 334 passing automated tests, including engine tests, model-validation tests, runtime integration tests, persistence tests, FastAPI endpoint tests, and an isolated end-to-end primary-flow smoke test. GitHub Actions runs the suite on pushes and pull requests to the development and main branches.

Validation demonstrates consistency of the implemented software contracts and workflows. It does not independently validate the correctness of every domain interpretation supplied to the engine.

8. Architectural Boundary

The public implementation rules include a thin application entry point, engine-contained runtime logic, model-centered contracts, and a strict separation between development tooling and runtime dependencies. AI assistants may be used as development tools, but the runtime itself is not designed to depend on external AI assistants.

The stable prototype should therefore be understood as a deterministic evidence-processing architecture: it maintains a living state model, preserves uncertainty through NULL, derives guarded recommendations, and requires explicit activation before mutation.

Conclusion

USE v0.1.0 establishes a continuously tested state-analysis prototype centered on evidence persistence, layered state derivation, uncertainty preservation, guarded action, and auditability. Its central engineering proposition is not that every system state can be known, but that a runtime can distinguish supported, unsupported, and unresolved evidence while keeping observation, recommendation, activation, and mutation as separate steps.
