UBL Kernel v1.0.0 · Public Whitepaper

Engineering the Universal Binary Language

Bit-0 Mechanics, Causal EventIDs, and Minimal-Framing Telemetry

With the tagging of ubl-kernel-v1.0.0, the Universal Binary Language (UBL) protocol freezes its core specification around an 8-bit atomic state-processing primitive designed for compact telemetry, deterministic state routing, bounded formal verification, and embedded-system execution.

Scope clarification: UBL does not claim that one byte can represent arbitrary structured information without context. Its claim is narrower: a fixed 8-bit atom combines a 7-bit state payload with one deterministic persistence-routing bit, while higher-level structure is supplied by ordered atom streams and protocol state.

1. The Bit-0 Kernel Primitive

At the center of UBL is the U-Atom: a single 8-bit value containing both a seven-bit payload and one memory/persistence-routing bit.

+-------------------------------+---+
| Payload Bits [7:1] (7 bits)  | M |
+-------------------------------+---+
                                    ^
                                    Bit 0
uint8_t payload = atom >> 1; // 7-bit payload: 0..127
uint8_t M       = atom & 1;  // 0 = volatile, 1 = persistent

Volatile state: M = 0

A non-control U-Atom with M=0 replaces volatile runtime state. Typical use cases include ADC readings, sensor telemetry, intermediate control values, and other short-lived runtime observations. These updates do not append to the persistent monotonic ledger.

Persistent state: M = 1

A non-control U-Atom with M=1 appends one occurrence to the monotonic persistent ledger. Examples include safety-state transitions, configuration locks, committed state changes, and fault conditions requiring retained history. Persistent atoms do not overwrite prior committed entries.

2. Control States and Escape Semantics

The frozen kernel reserves selected payload values for protocol control.

0x00  SYNC
0x01  START
0x02  END
0x03  ESC
0x7D  PATCH_HEADER
0x7E  WHY
0x7F  RESET

Because the raw U-Atom encoding is raw_atom = (payload << 1) | M, some control payloads correspond to two possible raw byte values depending on Bit 0. For example, ESC payload 0x03 maps to raw byte 0x06 or 0x07; RESET payload 0x7F maps to 0xFE or 0xFF.

Control payloads are decoded before ordinary persistence routing. RESET clears volatile execution state and returns framing logic to its reset state while preserving the persistent monotonic ledger. ESC allows reserved payload values to be transported as literal data rather than interpreted as control operators.

3. Dual-History Causal Architecture

UBL separates execution history from persistent semantic state. These are intentionally not the same thing.

Incoming U-Atom
      |
      v
Execution Identity Chain
      |
      +-----------------------+
      |                       |
     M=0                     M=1
      |                       |
volatile state         monotonic ledger

Execution Identity Chain

Every accepted U-Atom occurrence contributes to an execution identity chain, including ordinary payload atoms, volatile atoms, persistent atoms, control operators, escaped values, and RESET occurrences.

E_n = SHA256(E_(n-1) || Atom_n || uint64_be(n))

The sequence number is part of the hash material, so identical atom values appearing at different positions produce different EventIDs. Insertion, deletion, substitution, or reordering changes the downstream hash chain and is therefore detectable whenever a trusted previous state or trusted chain head is available. This should not be interpreted as authentication by itself; signatures or trusted key material are separate concerns.

Monotonic Ledger

The monotonic ledger records only accepted persistent state occurrences where M=1. Volatile observations and control events remain visible in execution history without becoming part of persistent semantic state. In practical terms, the execution chain answers “what exactly happened?”, while the persistent ledger answers “what became committed state?”

4. WHY Unwinding

UBL reserves payload 0x7E for the non-mutating WHY operator. WHY does not manufacture a causal explanation; it operates over recorded execution history. A runtime can traverse prior EventID occurrences to reconstruct the sequence leading to the current state without rewriting the history being inspected.

For this seven-bit-payload-plus-one-routing-bit workload, UBL reaches the same one-byte-per-event density as a hand-packed one-byte C representation. This means UBL adds no additional per-event wire-framing bytes in this test case; it does not mean zero total system overhead.

6. Embedded C99 Reference Demonstrator

A zero-dynamic-allocation C99 reference firmware harness has been implemented to exercise the frozen kernel in an embedded-style environment. The current implementation uses deterministic mock ADC input and mock GPIO output seams so that the runtime can be compiled and validated before deployment onto physical microcontroller hardware.

The reference firmware uses ubl_context_t and a caller-owned ubl_event_trace_t, routing atoms through ubl_process_atom() and ubl_event_trace_step().

The deterministic temperature sequence is 72, 79, 84, 86 with an over-temperature threshold of 80. Normal readings generate volatile telemetry atoms. When the threshold is exceeded, the firmware additionally emits a persistent safety atom, keeping high-frequency observation and committed safety state distinct.

uint8_t temperature = mock_adc_read(sample_index);
uint8_t telemetry_atom = encode_uatom(temperature, 0u);
ubl_process_atom(&runtime, telemetry_atom);
ubl_event_trace_step(&trace, telemetry_atom);

if (temperature > OVER_TEMPERATURE_C) {
    uint8_t safety_atom = encode_uatom(temperature, 1u);
    mock_gpio_cutoff(1);
    ubl_process_atom(&runtime, safety_atom);
    ubl_event_trace_step(&trace, safety_atom);
}

7. Cross-Runtime Conformance

The current validation and production acceptance suite reports 328 tests spanning Python runtime behavior, C99 interfaces and generation, JavaScript/WebAssembly behavior, Verilog parity models, DSL lowering, macro expansion, EventID consistency, mesh behavior, HIL fault handling, physical co-simulation, dynamic rebinding, and persistent-state invariants.

8. Formal Verification

UBL includes a finite-state formal verification path. DSL or assembly state models are lowered into finite transition systems and emitted as SMT-LIB2. Z3 evaluates properties including reachable states, invalid transitions, non-terminal deadlocks, invariant preservation, and persistent-schema immutability.

A solver-verified result means that the specific finite model lowered into the solver satisfies the checked properties under the modeled assumptions. It does not establish universal correctness for every arbitrary UBL program, future extension, or physical implementation.

9. Live Toolchain Validation

The validation workflow is configured to exercise real development tools rather than silently replacing unavailable native checks with behavioral substitutes. CI includes GCC, CMake, Node.js, Z3, Icarus Verilog, and Yosys for cross-runtime and hardware-oriented validation.

10. Kernel Boundary

The frozen v1 kernel consists of primitive rules governing eight-bit U-Atoms, Bit-0 persistence routing, control precedence, volatile state, monotonic persistence, execution occurrence identity, WHY behavior, RESET behavior, framing semantics, and observable runtime parity.

Higher-level systems—including assembly languages, DSLs, virtual machines, distributed mesh protocols, Byzantine consensus, browser runtimes, hardware bridges, physical simulation, development environments, and Universal State Engine integration—are extensions that can evolve without redefining the frozen primitive.

Conclusion

UBL v1.0.0 establishes a compact deterministic state primitive rather than attempting to replace arbitrary structured data formats with a single byte. Its core engineering proposition is specific: seven bits of state payload plus one bit of persistence intent form one U-Atom. From that primitive, the system derives a deterministic split between volatile and persistent state while maintaining a separate occurrence-aware cryptographic execution history.

The next meaningful validation milestone is execution of the frozen kernel on physical microcontroller and FPGA hardware using real sensor and actuator interfaces.
